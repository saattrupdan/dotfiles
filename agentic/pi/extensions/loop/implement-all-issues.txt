# Implement one issue per iteration

Complete the stages below for one issue before advancing to another.

## 1. Select and triage

Fresh GitHub issue selection (unassigned leaves and parents with all children closed):
{{PI_ISSUE_CANDIDATES}}.

- Select only from these issue numbers, except a new leaf sub-issue you create
  from a listed issue during this run. Verify GitHub's parent/sub-issue relationship.
- Among actionable eligible issues, prefer older issues over newer ones so old
  issues do not linger indefinitely.
- Prefer finishing partially completed parent groups over starting unrelated work:
  if some children are completed or ongoing, prioritise a remaining actionable,
  unassigned child. If all children are closed, prioritise the eligible parent
  and verify what remains. Within these groups, prefer older issues. These are
  selection preferences, not exceptions to eligibility, blockers, or claim rules.
- Never select or claim an issue labelled decision-blocked (or the repository's
  equivalent decision-blocker label). Skip it without revisiting its decision,
  removing its label, or repeatedly commenting. It becomes eligible only after
  the user or maintainer resolves the decision and removes that label.
- Before starting work, check for an existing open PR. Published work awaiting
  merge is not a fresh implementation task: do not duplicate its branch or PR.
  Claim it only if concrete active follow-up is needed on the existing work.
- Respect explicit user deferrals and permission limits. Historical engineering
  checkpoint labels do not turn unfinished work into a decision blocker.
- A parent with open children must wait. A parent whose children are all closed
  is eligible: inspect its full requirements and the children's implementations
  and merged PRs to determine whether anything remains. Closed children alone
  do not prove that the parent has been delivered.
- Before assigning, confirm the work fits one reasonably scoped PR. Investigate
  the code and existing evidence and resolve routine implementation and architecture
  choices yourself. Reproduction, diagnostics and research are engineering work;
  do not require the reporter to prove a reported bug before investigating it.
- Only a concrete user or maintainer decision about product behavior, scope,
  permission or risk can create a decision blocker. If that decision is genuinely
  required before safe progress, leave the issue unassigned and add a comment
  specifying the decision needed unless already documented. Apply the repo's
  existing standard decision-blocker label; if none exists, create a
  decision-blocked label and apply it. End this iteration normally.
- Other uncertainty, missing implementation, internal prerequisites, failed tests
  and incomplete verification remain actionable work, not blocker-label reasons.
  Follow Decision blockers and unfinished work below if you must pause.
- If too complex, break it into actionable sub-issues linked to the original
  issue as their parent. Reuse existing sub-issues rather than duplicating them.
  Leave the parent unassigned and choose only one actionable leaf sub-issue.
- If no actionable unassigned issue remains, report the blockers. Do not claim
  that blocked issues were implemented.

## 2. Claim before starting work

Run this command in ONE bash tool call from this repository checkout, replacing
ISSUE_NUMBER with the chosen positive issue number:

```sh
{{PI_ISSUE_CLAIM_COMMAND}}
```

- The helper acquires an atomic GitHub-side per-issue lock, freshly checks that
  the issue is open, unassigned, and has no open children, assigns the authenticated
  user, verifies the assignment and child completion, and releases the lock in
  that same invocation. This applies to eligible parents as well as leaves.
- Never split the check and assignment or bypass the helper with gh issue edit
  or direct assignment API calls. An existing assignment, even to @me, is not
  this session's ownership: skip that issue.
- Only exit 0 AND JSON status claimed for the selected issue permits implementation.
- Exit 3 (unavailable) or 4 (busy): choose another fresh candidate without changing
  its assignment or lock. For any other failure or uncertain result, do not
  implement or retry assignment. Record the exact claim uncertainty and recovery
  needed, without inventing a decision blocker, and end this iteration normally;
  never bypass or clear an uncertain claim.
- Never delete or expire a busy/retained lock automatically. Recovery requires
  confirming its owning session has stopped.
- Claim only one issue per iteration, including newly created leaf sub-issues.
  Never reuse a previous iteration's claim or treat an earlier assignment as yours.

## 3. Verify what remains, then implement if needed

- For a claimed parent, verify the current base checkout against the parent's full
  requirements, child implementations, merged PRs, and relevant checks. Inspect
  descendants where needed; do not assume closed or cancelled children delivered
  their requirements. Identify any missing integration, behavior, or acceptance work.
- If the parent is fully delivered and nothing remains, this is a close-only task:
  record concrete verification evidence. Do not invent code changes, create an
  unnecessary branch/commit, or open an empty PR. Still follow the review stage.
- Otherwise, create a feature branch and implement the remaining work, following
  repository rules. Run the relevant checks and tests; fix failures introduced by
  the change, subject to the validation exceptions below.
- Track the temporary resources you create so cleanup can distinguish them from
  pre-existing user resources and resources owned by other sessions.
- For visual changes, capture screenshots or a short video of the actual feature
  for the PR. Preserve that evidence before removing temporary test resources.
- Commit any implementation changes before requesting review.

### Validation exceptions

- Test timeouts do not block publication or advancement to the next issue, even
  when the change reproducibly causes the test or workflow to hang. Investigate
  and report what happened, including any change-induced hang; do not require a
  fix or a passing rerun before publishing. Run focused checks where useful, but
  do not repeatedly rerun expensive suites without a concrete reason. Create a
  normal review-ready PR, not a draft. Include exact commands, timeout limits,
  completed results, known hangs and outstanding verification in its description
  and iteration report. Never count timed-out tests as passing or close the issue
  as delivered on this evidence. Leave the PR open and move on after cleanup.
- For non-timeout test failures, establish whether the same failure occurs on the
  unchanged base. A pre-existing failure must be fixed in a separate PR, not mixed
  into the claimed issue's changes. Publish or retain the original issue PR as-is;
  implement, independently review and publish the separate fix PR in this iteration
  without claiming another issue. Apply the same publication, verification and
  cleanup rules to that PR. Add a review comment to the original PR identifying
  the baseline failure and linking the fix PR. Once the fix PR passes its checks
  (or meets the timeout exception), move on without waiting for it to merge or for
  the original PR to turn green. Do not claim the baseline failure already passes
  on the original PR. If the fix cannot be completed or verified under these rules,
  the verification gate remains unresolved.
- Other actual test failures introduced by the change must be fixed before
  publication. These exceptions do not waive unrelated review findings, build or
  lint errors, missing checks, or other unresolved verification failures.

## 4. Review until clean

1. Invoke one independent reviewer subagent on the complete implementation at the
   current commit. For a close-only parent, have it independently verify the parent
   requirements and delivery evidence, including whether any work remains. If it
   reports no remaining findings or changes needed, proceed to publishing; no
   additional review is needed for an unchanged clean result.
2. Otherwise, fix every actionable finding, including nits, run the relevant
   checks, clean up resources created for that fix round, and commit the fixes.
3. Invoke a NEW reviewer subagent on the updated complete implementation. Include
   the previous findings and how they were addressed. Repeat steps 2–3 until clean.

- If close-only review finds missing work, return to stage 3 and implement it
  before repeating review. Do not close the parent while requirements remain.
- LGTM with nits is not clean: address the nits and re-review.
- Do not substitute self-review, skip re-review after fixes, or impose an arbitrary
  review-round limit. If source changes after a clean review, check and review the
  updated commit before publishing.
- Give each reviewer the validation exceptions and supporting evidence. Report
  timeouts, including known change-induced hangs, and pre-existing failures, but
  do not let those exceptions alone prevent a clean review or publication. Other
  actionable findings still require fixes and a new independent review.
- Reviewer unavailability and correctable findings are engineering follow-up, not
  reasons for a blocker label. Retry or checkpoint and release your assignment if
  you must pause. Only a finding requiring a concrete user or maintainer decision
  qualifies for decision-blocked. Never publish or close without the required
  clean review.

## 5. Publish the result

- For a close-only parent, only after clean independent verification, add a comment
  explaining how its requirements were delivered, link the completed children/PRs
  and verification evidence, and close it as completed. Verify it is closed; no PR,
  feature branch, or new implementation commit is required.
- For implemented changes, rerun the relevant checks and tests on the final reviewed
  commit after all review fixes. Once that commit has a clean independent review
  and checks pass or meet the validation exceptions, push all implementation commits
  and create a normal review-ready PR. Include any validation exceptions and their
  evidence in the description; never describe incomplete validation as passing.
  Assign me to the PR and copy all GitHub labels from the issue to it. Include
  visual evidence when applicable. Verify it contains the reviewed commits.
- Once the PR exists and all implementation commits are pushed, preserve evidence
  and deliverables, return to the base checkout, and discard this task's local
  feature branch and worktree. For a Pi-managed isolated branch, call
  discard_isolated_branch, not clean_up_isolated_branch (which requires a merge).
  Keep the remote branch and PR intact; do not wait for CI or merge to remove the
  local copies. Never discard unpushed work or unrelated local changes.
- After publication and owned cleanup, release this iteration's issue assignment
  and verify removal. Waiting for CI, review or merge is not an assignment reservation;
  retain it only while actually performing active follow-up. Keep the PR author
  assigned to the PR. Leave the issue open until its merged result meets acceptance.

## 6. Verify PR checks and tests before advancing

- For every PR created or updated in this iteration, inspect all checks and tests
  on its latest head commit, not just branch-protection-required checks. Wait for
  them to finish and pass unless the validation exceptions apply. Use gh to inspect
  the PR's checks and workflow runs; local success alone does not establish PR CI
  success. Confirm the expected checks actually ran.
- Pending, queued, running, failed, cancelled, timed-out, missing, or unavailable
  checks are not passing. A skipped or neutral check is acceptable only when you
  verify it is intentionally inapplicable; never count skipped tests as executed.
  The timeout and linked baseline-fix exceptions permit advancement, not a claim
  that failing or incomplete checks passed. If the repository has no PR CI
  configured, verify that explicitly and record local check/test outcomes and any
  validation exceptions against the exact PR head commit.
- For failures outside the validation exceptions, diagnose and fix their causes,
  rerun the relevant checks and tests, and
  repeat the clean independent review stage for source changes. If local changes
  are needed, recreate a task branch/worktree from the PR's remote head. Push the
  fixes to the same PR, discard those local copies after verifying the push, and
  wait again. Any new head commit invalidates earlier CI evidence;
  recheck all PRs against their current heads before advancing.
- Record each PR URL, verified head SHA, check/test outcomes and evidence for any
  validation exceptions in the iteration report. Do not merge a PR merely to
  satisfy this gate. Timeouts and baseline failures covered by a linked verified
  fix PR do not leave this gate unresolved: leave the PRs open, clean up and move on.
- Otherwise, do not select or claim the next issue while this gate is unresolved.
  If you cannot finish verification, preserve published work in the remote branch
  and PR, discard the task's local branch/worktree once all commits are pushed,
  record the exact failing or unavailable checks and recovery steps, clean up
  owned disposable resources, release this iteration's issue assignment, and call
  /loop stop. Outside the validation exceptions, never advance past an unverified
  PR. Do not label it decision-blocked unless a concrete user or maintainer
  decision is required.
- Close-only parents with no created or updated PR retain their independent
  verification requirement; no empty PR or artificial CI run is needed.

## 7. Clean up before advancing

- Stop and remove temporary testing applications, dev/test servers, containers,
  browser sessions/profiles, disposable databases/test data, and scratch files
  created by this iteration, including resources created by subagents.
- Perform this runtime cleanup on failure or interruption too. Remove only
  resources you can identify as belonging to this iteration; never stop unrelated
  processes or delete pre-existing apps, user data, or another session's resources.
- Preserve PR evidence and any required deliverables. Verify owned temporary
  resources are gone; if cleanup fails, diagnose it and document the exact owned
  resources still remaining. Cleanup failure alone is not a decision blocker.
  Do not hide cleanup failures or touch unrelated resources.
- Verify published tasks have no remaining local feature branch or worktree;
  discard any task-owned copies recreated for follow-up once committed and pushed.
  Keep the remote branch and PR intact and preserve unrelated local changes.
  Close-only tasks must not create branches/worktrees just to clean them up.
  Follow repository rules when they prohibit branches/worktrees.
- If you must pause with unpublished or unpushed implementation work, preserve it
  in its feature branch/worktree, but release this iteration's issue assignment
  as below.
  Commit a checkpoint if needed for the automatic return to base; never discard
  unfinished changes or delete an unfinished task's branch/worktree. Clean up only
  disposable runtime resources and leave unrelated local changes untouched.

## Decision blockers and unfinished work

Create a blocker only when a concrete user or maintainer decision is required.
Not finishing an iteration does not make the issue blocked. Failed or stalled
checks, reproduction, research, missing code, review fixes, unavailable reviewers,
internal dependency order, time limits and resource contention are engineering work.
Do not create or apply a generic blocked label for any of these reasons.

- Continue investigating and fixing actionable work under the validation
  exceptions and PR verification gate above. Publish and advance on documented
  timeouts, including change-induced hangs; isolate pre-existing failures in a
  separate linked fix PR. Never report these outcomes as passing tests. Diagnose
  contention instead of blindly repeating expensive full test runs alongside
  other agents.
- If a concrete decision is required, comment with the exact decision, why safe
  progress depends on it, progress/evidence and retained work. Apply only the
  repository's decision-blocker label, or decision-blocked if none exists.
- If you must pause without such a decision, leave the issue open and actionable.
  Record a recoverable checkpoint, remaining engineering steps and retained
  resources, without applying a blocker label or calling the pause decision-blocked.
  An external constraint alone does not justify creating a label unless a concrete
  user or maintainer decision is needed. Respect existing explicit user deferrals.
- Update existing handoff comments rather than repeating unchanged information.
- Assignment means active work, not a reservation. If this iteration successfully
  claimed the issue and is no longer actively working on it, remove the authenticated
  user's assignment added by that claim and verify removal. This includes paused
  work, decision-blocked work and published PRs that are only waiting for merge.
  An issue never claimed by this iteration stays unassigned.
- Remove only this iteration's confirmed assignment. Never take over or remove
  another session's assignment or lock, including a pre-existing @me assignment.
  An uncertain claim is not proof of ownership: do not clear its lock or guess whose
  assignment to remove. Document the uncertainty and any recovery needed.
- If GitHub is unavailable or unassignment fails, report exactly which comment,
  label, or assignment updates could not be made instead of claiming success.
- Clean up owned disposable runtime resources and preserve unfinished work as above.
- Except when the unresolved PR verification gate above requires /loop stop, end
  this iteration normally with a concise decision or engineering-handoff report.
  Otherwise, do not call /loop stop, request that the whole loop stop, emit a
  special stop token, or treat the issue as
  implemented. The loop's normal --until check decides whether actionable issues
  remain and starts the next iteration when they do.

Only when no actionable unassigned issue remains should the loop finish. Unfinished
engineering remains actionable even when an earlier agent paused or called it
blocked. A decision-blocked issue is skipped, not implemented or counted as
unfinished engineering that this agent can resolve. Busy/unavailable candidates
alone are not decision blockers; try another fresh candidate.
